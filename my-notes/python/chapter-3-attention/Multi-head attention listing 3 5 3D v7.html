1aX and W_q

self.W_query = nn.Linear(d_in, d_out, bias=qkv_bias)
X(b, 6, 3)
W_q(3, 4) = (d_in, d_out)

X is 6 tokens, each described by 3 numbers: d_in = 3.

W_q maps those 3 numbers to 4: d_out = 4. Its blue columns are head 0’s weights, the green are head 1’s. The wrapper (Listing 3.4) kept these as two separate 3×2 matrices; here they sit side by side in one 3×4.

nn.Linear stores W as (d_out × d_in) and transposes internally. Same math.

1bQ = X · W_q

queries = self.W_query(x)   # same for keys, values
X · W_q(b, 6, 3) → (b, 6, 4)

One matmul makes all 4 columns at once. Columns 0–1 are head 0’s query, columns 2–3 are head 1’s. Each head gets head_dim = d_out / num_heads = 2 columns.

Keys and values are made the same way: W_key and W_value are also single 3×4 matrices, one matmul each, giving K and V of shape (b, 6, 4). They go through steps 2–3 exactly like Q. The model only draws Q, to keep it readable.

This is the efficiency win of the whole class: the wrapper (Listing 3.4) ran a separate Q, K and V matmul for every head, but here each is one matmul, however many heads there are. Matmuls are the expensive step.

The 4 columns become 2 heads × 2 numbers. In the model, the green columns fold in behind the blue: the depth axis is now head_dim.

In memory nothing moves. It’s the same 24 numbers in the same order, just relabelled. Read (6, 2, 2) as 6 token slices, each 2×2. The orange outline is item [0]: “Your”, with both heads.

That’s why the assert needs d_out % num_heads == 0: the fold has to land between columns.

3.transpose(1, 2): slice the other way

queries = queries.transpose(1, 2)
axis0123
beforebtokensheadshead_dim(b, 6, 2, 2)
afterbheadstokenshead_dim(b, 2, 6, 2)

Same 24 cubes, sliced lengthways instead of across: 2 long slices, one per head, each 6×2. Item [0] is now head 0 with all 6 tokens.

Then the block flips over its diagonal, which is exactly what transposing does, so the axes point the same way as in step 2: axis 1 runs down, axis 2 runs across, axis 3 is depth. Heads now go down the side and tokens go across.

Each slice is an ordinary 6×2 query matrix, exactly like one CausalAttention would make. It’s (1, 2) and not (0, 1) because axis 0 is the batch b.

4aQ @ Kᵀ: scores, then the mask

attn_scores = queries @ keys.transpose(2, 3)
mask_bool = self.mask.bool()[:num_tokens, :num_tokens]
attn_scores.masked_fill_(mask_bool, -torch.inf)
scores(b, 2, 6, 2) @ (b, 2, 2, 6) → (b, 2, 6, 6)

Attention scores: the raw query·key dot products. Score (i, j) says how relevant token j is to token i.

K has been through steps 1–3 too, so it’s (b, 2, 6, 2), the same shape as Q. It isn’t drawn; only the resulting scores are.

@ only multiplies the last two axes, so it runs once per head: each long slice (6×2) times Kᵀ (2×6) gives a 6×6 slab. Rows are query tokens, columns are key tokens.

This is why step 3 mattered. Before it, the last two axes were (heads, head_dim), and @ would have compared the two heads inside a single word.

keys.transpose(2, 3) is a different job from step 3: it swaps the last two axes to make Kᵀ. The faded cubes are future tokens, masked to −∞.

The mask itself is built once in __init__: torch.triu(..., diagonal=1) puts 1s above the diagonal, i.e. on future tokens. register_buffer stores it inside the module so it moves to the GPU with the model, but it isn’t a weight and is never trained. It’s context_length × context_length, so [:num_tokens, :num_tokens] cuts it down when the input is shorter. Same as CausalAttention in §3.5.

4bsoftmax: attention weights

attn_weights = torch.softmax(
    attn_scores / keys.shape[-1]**0.5, dim=-1)
weights(b, 2, 6, 6) → (b, 2, 6, 6)

Attention weights: the scores after scaling, masking and softmax. Each row sums to 1, so row i says what share of attention token i gives each token.

Cube height is now the attention weight. The masked cubes become 0.

keys.shape[-1] is head_dim, so the scaling is ÷ √2, not ÷ √d_out. Dropout also happens here; it doesn’t change the shape.

4c@ values: context per head

attn_weights @ values
context(b, 2, 6, 6) @ (b, 2, 6, 2) → (b, 2, 6, 2)

Context vector: a token’s new vector, made as a weighted sum of the value vectors of itself and earlier tokens, using its attention weights. It’s the token’s meaning with its context mixed in. In MNIST terms, it’s like a hidden-layer output for one token, but the mixing weights are computed fresh for each input instead of being fixed learned weights.

V has been through steps 1–3 too, so it’s (b, 2, 6, 2), the same shape as Q. It isn’t drawn; only the resulting context is.

Each head’s 6×6 weights times its 6×2 values gives a 6×2 context slice. We’re back to two long slices, one per head, the same shape as the queries after step 3, so it’s drawn in the same orientation: axis 1 (heads) down, axis 2 (tokens) across.

In the book this is the first half of the line context_vec = (attn_weights @ values).transpose(1, 2).

axis0123

The shape doesn’t change, so the output keeps the same axes as 5b: axis 1 = tokens (6) down, axis 2 = d_out (4) across. The brackets are drawn on the output.

A normal dense layer, like one in your MNIST net: context (6×4) × W_o (4×4) = output (6×4).

W_o’s rows line up with the context’s columns: its top two rows (blue) multiply head 0’s columns and its bottom two (green) multiply head 1’s. Every output column uses all four rows, so every output number draws on both heads (purple = mixed). Before this, the heads never met.

Optional (see appendix B) but standard in real LLMs. Bias omitted here.
